Je te conseille de concevoir SpeakFlow comme un véritable projet logiciel, avec une architecture qui te permette de commencer simplement en Python, puis d'ajouter des fonctionnalités sans devoir tout réécrire.

Je vais te donner un prompt complet à fournir à une IA de développement (ChatGPT, Claude, Cursor, etc.), accompagné d'une architecture technique solide, des responsabilités de chaque module et d'un ordre de développement progressif.

L'objectif est double : créer une application réellement utile pour pratiquer l'anglais à l'oral et apprendre Python en développant un projet que tu pourras présenter dans ton portfolio.

# 1. Architecture recommandée pour SpeakFlow

Je recommande une architecture modulaire avec Python, FastAPI, React et TypeScript pour la version pérenne. C'est un peu plus exigeant que Streamlit, mais cela te fera travailler sur un véritable backend Python et une interface web moderne.

Frontend — React + TypeScript

Interface, microphone, lecteur audio, transcription et progression

HTTPS / REST API · JSON · Audio multipart

Backend — Python + FastAPI

API, validation, règles métier, orchestration des sessions et sécurité

Services IA

Conversation, transcription, synthèse vocale et feedback

Persistance

SQLAlchemy + SQLite au départ, PostgreSQL ensuite

Infrastructure et qualité

pytest · Ruff · Docker · GitHub Actions · logs structurés

### Pourquoi cette architecture ?

- React + TypeScript : une interface claire, interactive et adaptée à l'enregistrement audio.
- FastAPI : tu apprends à créer une API Python, à valider des données et à séparer la logique métier.
- Pydantic : tu définis précisément les données entrantes et sortantes.
- SQLAlchemy : tu sépares le code métier de la base de données.
- SQLite puis PostgreSQL : tu peux démarrer localement sans serveur de base de données.
- Une couche de services IA : tu pourras changer de fournisseur sans modifier toute l'application.
- Docker et CI/CD : tu pourras apprendre les bases du déploiement et de l'automatisation après avoir obtenu un MVP fonctionnel.

Le point essentiel est de conserver une architecture modulaire sans multiplier les microservices. Pour ce projet, un monolithe modulaire est largement suffisant.

| Couche               | Responsabilité                                           |
| -------------------- | -------------------------------------------------------- |
| `api/`               | Recevoir les requêtes HTTP et retourner les réponses     |

## 4. Concevoir une API claire

Voici les endpoints que je définirais pour la première version.

| Méthode | Endpoint                              | Fonction                                         |
| ------- | ------------------------------------- | ------------------------------------------------ |
| `GET`   | `/api/v1/health`                      | Vérifier que le backend fonctionne               |
| `POST`  | `/api/v1/sessions`                    | Créer une session d'apprentissage                |
| `GET`   | `/api/v1/sessions/{id}`               | Consulter une session                            |
| `POST`  | `/api/v1/sessions/{id}/turns`         | Envoyer une réponse audio et obtenir un feedback |
| `POST`  | `/api/v1/sessions/{id}/next-question` | Générer la question suivante                     |
| `POST`  | `/api/v1/audio/transcriptions`        | Transcrire un fichier audio                      |
| `POST`  | `/api/v1/audio/speech`                | Générer un fichier audio à partir du texte       |
| `GET`   | `/api/v1/progress`                    | Consulter la progression                         |
| `GET`   | `/api/v1/vocabulary/reviews`          | Récupérer les mots à réviser                     |

Pour le MVP, tu peux réduire cette liste et fusionner certaines opérations. Par exemple, l'envoi d'un tour de conversation peut transcrire l'audio, générer le feedback et sauvegarder les données dans un seul parcours applicatif.

Quelques conventions importantes :

- Préfixer les routes avec `/api/v1` pour préparer de futures évolutions.
- Utiliser des schémas Pydantic pour toutes les entrées et sorties.
- Retourner des erreurs HTTP explicites et cohérentes.
- Définir des limites de taille et de durée sur les fichiers audio.
- Ne jamais exposer les clés API ou les secrets au frontend.
- Documenter les contrats d'API et tester les principaux scénarios.

# 5. Le prompt complet pour développer SpeakFlow avec une IA

Tu peux copier ce prompt dans ChatGPT, Claude ou un assistant de programmation. Il définit le produit, l'architecture, les contraintes techniques et surtout la façon dont l'IA doit t'accompagner dans ton apprentissage de Python.

# Projet SpeakFlow — Spécification produit et technique

## 1. Rôle

Tu es un développeur senior Python spécialisé en FastAPI, React, TypeScript, applications utilisant des modèles d'intelligence artificielle et architecture logicielle maintenable. Tu es également un mentor pédagogique capable d'accompagner un développeur qui maîtrise déjà les bases de Python et souhaite progresser en développant un projet réel.

Tu dois m'aider à concevoir et développer une application appelée **SpeakFlow**, dont l'objectif est de m'aider à apprendre l'anglais à l'oral et à améliorer ma compréhension orale, tout en me permettant d'apprendre Python.

Ne génère pas tout le projet en une seule fois. Travaille progressivement, explique tes choix techniques et attends ma validation avant de passer aux grandes étapes suivantes.

## 2. Présentation du projet

SpeakFlow est une application web d'apprentissage de l'anglais centrée sur la pratique orale et la compréhension.

L'utilisateur doit pouvoir :

- écouter des questions en anglais ;
- répondre en anglais à l'aide de son microphone ;
- obtenir une transcription de sa réponse ;
- recevoir des corrections grammaticales et des reformulations naturelles ;
- comprendre ses erreurs grâce à des explications en français ;
- écouter les phrases corrigées ;
- poursuivre une conversation avec une IA ;
- enregistrer ses sessions et consulter sa progression ;
- retrouver les expressions et mots qu'il doit réviser.

Le principe pédagogique est de privilégier la pratique active : l'utilisateur doit essayer de comprendre et de répondre avant de consulter les corrections.

L'interface peut être en français, mais les exercices et les conversations doivent se dérouler principalement en anglais.

## 3. Utilisateur cible

Le développeur du projet :

- connaît les bases de Python ;
- souhaite progresser en programmation backend ;
- veut construire un projet concret pour son portfolio ;
- souhaite améliorer son anglais parlé et sa compréhension orale ;
- souhaite apprendre les bonnes pratiques de développement logiciel.

L'application doit être utilisable personnellement dès le MVP, sans imposer la création d'un compte utilisateur.

## 4. Stack technique

### Frontend

- React
- TypeScript
- Vite
- Une bibliothèque de composants légère ou des composants personnalisés
- Un client HTTP centralisé
- React Router si plusieurs pages sont nécessaires
- Gestion explicite des états de chargement, des erreurs et des enregistrements audio

### Backend

- Python
- FastAPI
- Pydantic pour la validation des données
- SQLAlchemy pour l'accès aux données
- Alembic pour les migrations de base de données
- SQLite en développement
- PostgreSQL lorsque le déploiement ou les besoins le justifient

### Intelligence artificielle

Créer une couche d'intégration indépendante du fournisseur d'IA.

Elle doit permettre de :

- transcrire les réponses audio en texte ;
- générer des questions conversationnelles ;
- corriger les réponses anglaises ;
- produire des explications pédagogiques en français ;
- générer des réponses audio à partir de texte.

Le fournisseur et les modèles doivent être configurables. Ne suppose pas qu'un modèle particulier est disponible sans vérifier la documentation correspondante.

### Qualité et infrastructure

- pytest pour les tests backend
- Ruff pour le linting et le formatage Python
- TypeScript strict
- Tests frontend adaptés aux composants critiques
- Docker et Docker Compose
- GitHub Actions pour l'intégration continue
- Logs structurés et configuration par variables d'environnement

## 5. Architecture logicielle

Utiliser un monolithe modulaire. Ne pas introduire de microservices dans le MVP.

Séparer les responsabilités entre :

- API et endpoints HTTP ;
- schémas de validation ;
- services métier ;
- repositories d'accès aux données ;
- modèles de persistance ;
- intégrations externes d'IA et d'audio ;
- configuration, sécurité et journalisation ;
- frontend organisé par fonctionnalités.

Les endpoints ne doivent pas contenir toute la logique métier.

Les services ne doivent pas dépendre directement des composants React ni des détails HTTP.

Les accès à la base de données doivent être centralisés dans les repositories ou dans une couche d'accès clairement définie.

Les appels à l'IA doivent être encapsulés afin de faciliter leur remplacement, leur simulation pendant les tests et la gestion des erreurs.

Évite les abstractions inutiles. L'architecture doit rester proportionnée à la taille du projet.

## 6. Fonctionnalités du MVP

### A. Sessions de conversation

- Créer une session avec un objectif pédagogique.
- Choisir un niveau de difficulté initial.
- Générer une question adaptée au contexte.
- Enregistrer les messages de l'utilisateur et de l'IA.
- Permettre de poursuivre ou de terminer une session.

### B. Audio et transcription

- Enregistrer une réponse au microphone depuis le navigateur.
- Envoyer le fichier audio au backend.
- Valider son format, sa taille et sa durée.
- Transcrire la réponse en anglais.
- Afficher la transcription à l'utilisateur.
- Gérer les erreurs d'enregistrement et de transcription.

### C. Corrections pédagogiques

Pour chaque réponse, produire une structure de données validée contenant :

- la transcription originale ;
- une version corrigée ;
- une reformulation plus naturelle si nécessaire ;
- les erreurs importantes ;
- des explications en français ;
- du vocabulaire utile ;
- une question de suivi adaptée à la conversation.

Ne pas inventer d'erreurs lorsque la réponse est correcte. Distinguer les erreurs grammaticales des simples améliorations stylistiques. Adapter la complexité des explications au niveau de l'utilisateur.

### D. Compréhension orale

- Faire écouter une question ou un court extrait en anglais.
- Ne pas afficher automatiquement la transcription avant la réponse.
- Demander à l'utilisateur de répondre ou de résumer ce qu'il a compris.
- Révéler ensuite la transcription et les explications.
- Enregistrer les résultats.

### E. Progression

- Enregistrer les sessions et leurs résultats.
- Conserver les mots et expressions utiles.
- Afficher les erreurs récurrentes.
- Préparer une liste de révision.
- Afficher des statistiques simples.

Ne prétends pas mesurer précisément l'accent ou la prononciation uniquement à partir d'une transcription.

## 7. Modèle de données initial

Proposer et justifier un modèle relationnel comprenant au minimum :

### Session

- id
- objectif pédagogique
- niveau
- date de création
- date de fin éventuelle
- statut

### Message

- id
- session_id
- rôle : utilisateur ou assistant
- contenu textuel
- date de création

### Feedback

- id
- message_id
- transcription
- texte corrigé
- reformulation naturelle
- explications
- données de vocabulaire utiles

### VocabularyItem

- id
- expression anglaise
- signification française
- phrase d'exemple
- date de prochaine révision
- niveau de maîtrise

Adapter ce modèle si une autre structure est plus cohérente. Éviter de stocker des fichiers audio durablement si cela n'est pas nécessaire au MVP.

## 8. Sécurité et robustesse

- Ne jamais exposer les clés API dans le frontend.
- Charger les secrets depuis des variables d'environnement.
- Fournir un fichier .env.example sans secrets réels.
- Ajouter .env et les fichiers sensibles au .gitignore.
- Valider les entrées et les fichiers audio.
- Ajouter des délais d'expiration, des limites de taille et une gestion des erreurs pour les appels externes.
- Éviter de journaliser les secrets, les fichiers audio ou les données personnelles inutiles.
- Ne pas considérer les réponses générées par l'IA comme des données fiables sans validation.
- Prévoir des tests avec des réponses IA simulées afin de limiter les coûts pendant le développement.

L'absence d'authentification est acceptable pour un MVP local à usage personnel. Si l'application est déployée publiquement ou devient multiutilisateur, expliquer les mesures nécessaires pour protéger les sessions, les données et les coûts d'utilisation.

## 9. Organisation du développement

Procéder dans cet ordre :

1. Définir les exigences, les parcours utilisateur et les critères d'acceptation.
2. Proposer l'architecture et l'arborescence du dépôt.
3. Mettre en place le projet Python et l'environnement virtuel.
4. Créer une première API de santé et un premier test automatisé.
5. Développer les questions et réponses sans IA, avec des données simulées.
6. Construire l'interface React et la connecter à l'API.
7. Ajouter la persistance SQLite et les migrations.
8. Ajouter l'enregistrement audio et la transcription.
9. Ajouter les corrections pédagogiques par IA.
10. Ajouter la synthèse vocale et les exercices de compréhension.
11. Ajouter les statistiques et les révisions.
12. Ajouter les tests, Docker, la documentation et le déploiement.

Chaque étape doit aboutir à une version exécutable et vérifiable.

## 10. Mode pédagogique obligatoire

Je veux apprendre Python en réalisant ce projet, pas seulement obtenir du code généré automatiquement.

Pour chaque fonctionnalité :

- explique le problème que nous cherchons à résoudre ;
- identifie les notions Python à apprendre ;
- explique pourquoi tu choisis cette approche ;
- commence par un petit exercice si cela est pertinent ;
- propose une implémentation simple ;
- explique le code et ses responsabilités ;
- ajoute les tests nécessaires ;
- indique comment vérifier manuellement le résultat ;
- propose une amélioration facultative.

Privilégie du code lisible et idiomatique. Évite les abstractions prématurées, les dépendances superflues et les fichiers trop volumineux.

Ne génère pas plusieurs milliers de lignes de code en une seule réponse. Fournis les fichiers nécessaires à l'étape en cours, avec leur chemin exact, et vérifie la cohérence des imports et des interfaces.

Si une information est manquante, formule une hypothèse raisonnable et explicite plutôt que de bloquer inutilement le projet. Pose une question uniquement lorsqu'une décision importante ne peut pas être prise sans moi.

## 11. Critères d'acceptation du MVP

Le MVP sera considéré comme fonctionnel lorsque :

- l'application démarre localement avec une procédure documentée ;
- l'utilisateur peut créer et terminer une session ;
- il peut écouter une question et enregistrer sa réponse ;
- le backend peut transcrire cette réponse ;
- l'IA fournit une correction structurée et pédagogique ;
- l'utilisateur peut écouter la formulation corrigée ;
- la session et son historique sont conservés après redémarrage ;
- les erreurs courantes sont affichées proprement ;
- les principaux services possèdent des tests automatisés ;
- les secrets ne sont pas exposés dans le navigateur ;
- le README explique l'installation, la configuration et l'utilisation.

## 12. Première tâche

Ne commence pas à coder l'ensemble de l'application.

Commence par fournir :

1. un résumé fonctionnel du MVP ;
2. les décisions d'architecture avec leurs justifications ;
3. une première arborescence réaliste ;
4. un diagramme du parcours d'une conversation ;
5. les principales entités de la base de données ;
6. les premières routes de l'API ;
7. un plan de développement découpé en petites étapes ;
8. les notions Python que je vais apprendre à chaque étape.

Termine en me proposant uniquement la première étape pratique à réaliser. Attends ma validation avant de poursuivre.

## 6. Trois règles pour éviter les problèmes dès le début

1. Ne mélange pas apprentissage et génération automatique. Demande à l'IA de t'expliquer les fichiers et de te proposer des exercices avant de générer toute la solution. Sinon, tu risques d'obtenir un projet fonctionnel sans comprendre comment il fonctionne.
2. Utilise des données simulées avant de payer une API. Commence avec des questions, transcriptions et corrections fictives. Branche les vrais services d'IA uniquement lorsque le parcours complet fonctionne.
3. Développe par petites fonctionnalités testables. Chaque étape doit être exécutable, testée et enregistrée dans Git avant de passer à la suivante.

## 7. L'ordre dans lequel je commencerais concrètement

Pour ton premier sprint, je ferais uniquement ceci :

- Créer le dépôt Git `speakflow`.
- Installer Python, Node.js et créer les environnements nécessaires.
- Initialiser FastAPI et React.
- Créer `GET /api/v1/health`.
- Afficher une première page React qui vérifie que le backend répond.
- Écrire un premier test avec `pytest`.
- Documenter les commandes de lancement dans le README.

Tu auras alors une application vide, mais une base technique saine sur laquelle tu pourras construire chaque fonctionnalité.

Mon conseil final : garde React + FastAPI comme architecture cible si tu souhaites un projet de portfolio professionnel. N'ajoute toutefois ni authentification complexe, ni Kubernetes, ni architecture distribuée au départ. Ton premier objectif est de faire fonctionner une conversation vocale de bout en bout, puis d'améliorer progressivement la qualité du code, les tests et le déploiement.
